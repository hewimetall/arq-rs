# Тестирование

Статус: нормативный контракт от 2026-11-23. Эти тесты обязаны появиться вместе с первой реализацией соответствующего поведения. Зелёный набор на старых ключах Apalis их не заменяет.

Тесты гоняются против Redis 8.6.2. Отдельная группа поднимает Redis Cluster и рвёт соединение на redirect. Python hooks, которые контракт относит к child, выполняются в реальном child-процессе, а не только вызовом `dispatch` в том же интерпретаторе.

## Протокол Redis

- Два параллельных `enqueue` с одним `unique_key` создают одну задачу. Второй ответ — `duplicate`. Ошибка Redis этим ответом не подменяется.
- Потерянный ответ `EXEC` для `enqueue`, `claim`, `renew`, `finish`, `requeue` и `control` восстанавливается чтением receipt и постусловий. Повтор с теми же параметрами не создаёт вторую задачу, вторую доставку и второй цикл.
- Тот же `operation_id` с другими параметрами возвращает `OperationConflict`.
- Частичный ответ `EXEC` даёт `StorageInconsistency`: процесс больше не пишет эту очередь, индекс сам не чинит, uniq сам не снимает.
- Обрыв соединения и redirect Cluster во время транзакции начинают цикл заново, если ответ `EXEC` не был отправлен. Если отправлен и не прочитан, путь неизвестного исхода.
- Повтор конфликта `WATCH` ограничен `ARQ_WATCH_RETRIES`.
- `renew` и `finish` со старым token или старым `cycle_id` задачу не меняют.
- `started_at_ms` после renew совпадает с первым значением доставки.

## Доставка и процессы

- `SIGKILL` до входа в handler оставляет уже увеличенный `deliveries` и не пишет исход handler. Следующий claim создаёт новую доставку.
- `SIGKILL` после входа в handler ведёт себя так же: исход не синтезируется.
- Серия падений до handler исчерпывает `max_deliveries` раньше `max_retries` и пишет DLQ `max_deliveries`.
- Прикладные retry держат uniq. `done` и `dead` снимают его только если значение равно `task_id`.
- DLQ ищется по tag через `dead_for_tag`. Retention удаляет hash, историю и оба индекса одной задачей. Активный uniq batch не удаляет.
- Requeue из DLQ сохраняет `task_id` и сообщение, обнуляет счётчики, меняет `cycle_id` и заново берёт uniq. Занятый uniq оставляет задачу в DLQ.
- Повтор requeue не создаёт второй цикл. Команда старого цикла новую выдачу не блокирует.
- При пустом ready просроченный inflight выдаётся снова. При непрерывном потоке новых ready-задач просроченный inflight тоже проверяется на каждом опросе.
- Зависший поток loop исчерпывает ping budget и даёт код 2. `asyncio.sleep` внутри handler budget не исчерпывает.
- Shutdown с активной доставкой продолжает renew, фиксирует успевший исход и вызывает `on_stop`. Истечение shutdown timeout ACK не пишет.
- Краткий отказ Redis перезапускает слот с паузой от 1 с до 30 с и не создаёт плотный цикл respawn.

## Python

- Четыре middleware в реальном child повторяют порядок simple-q: `on_send`, `on_start`, `on_stop` и `on_dead` в порядке регистрации; `around_dispatch` входит снаружи внутрь и выходит изнутри наружу.
- `current_message()` виден внешнему `around_dispatch` и равен `None` после успеха, исключения и кооперативной отмены.
- `on_dead` выполняется до возврата `dispatch` и до commit Redis. Внешний middleware, заменивший `dead` на `retry`, оставляет hook уже вызванным, а Rust записывает retry.
- Ошибка одного `on_dead` логируется, остальные hooks списка вызываются, возвращённый словарь остаётся прежним.
- Ошибка `on_start` логируется, следующие start hooks выполняются, child переходит к claim.
- Исключение самого `dispatch` даёт `dispatch_error` и не ставит retry.
- Словарь без `outcome` и словарь с неизвестным `outcome` дают `invalid_outcome`, а не ACK.
- Timeout с подавленной отменой: словарь, вернувшийся до конца `cancel_grace_ms`, фиксируется; молчание дольше grace убивает child и finish не пишет.
- Неизвестный actor даёт `unknown_actor` и вызывает `on_dead` до commit.

## Управление

- `cancel` и `kill` задачи `ready` сразу пишут DLQ. `inflight` сохраняет команду, обычный finish отвергается, новый claim эту доставку не создаёт.
- Команда, пришедшая после успешного finish, видит `already_terminal`.
- После рестарта supervisor принятая inflight-команда читается из hash. Процесс, который нельзя связать со slot и token, сигнал не получает, и задача заново не выдаётся.
- Подавленная cancel оставляет команду, child выходит, и только наблюдаемый выход позволяет терминальный commit.
- Автоматического перехода cancel в kill нет.
- Admin после смерти child показывает код выхода и не оставляет завышенный in-progress gauge. Чтение admin не продлевает lease и не удаляет битый индекс: отсутствующий hash виден как `missing_job`.

## Синтетические данные

Публичные примеры, fixtures и тесты используют только эти имена: обработчик `process_item`, очередь `default`, аргумент `item_id`, ключ уникальности вида `item:<число>`, tag `batch-a` или `batch-b`, URL `redis://redis:6379/0`.

Проверка репозитория отклоняет `@actor` с другим именем функции в `docs/` и тестовых fixtures. Предметные имена приложений-потребителей в эти каталоги не добавляются.
